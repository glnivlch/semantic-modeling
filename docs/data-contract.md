# Предварительный договор между модулями

**Проект:** система семантического моделирования предметной области «Промышленное оборудование» с динамическими графами знаний и взаимодействием на естественном языке.

**Статус:** проект для обсуждения командой, не утверждённая спецификация.

**Версия документа:** 0.3.

## 1. Назначение, базовый прототип и итоговый MVP

Договор задаёт одинаковые названия полей и правила обмена данными для четырёх направлений команды. Это позволит разрабатывать модули независимо, не меняя смысл данных при передаче.

Технологии проекта: Python 3.12, NetworkX, SQLite, Dash + Cytoscape, pytest. Обработка естественного языка начинается со словарей и правил; Natasha подключается только при необходимости.

### 1.1. Базовый прототип

Базовый прототип — первый технический этап, а не завершённый проект. Он включает:

- создание вершин и направленных связей;
- несколько отношений между одной парой объектов;
- сохранение в SQLite и восстановление графа;
- поиск вершин и получение соседей вершины.

Визуализацию и простой вопрос по правилам можно подключить для ранней демонстрации, но они не являются условием готовности базового ядра.

### 1.2. Итоговый MVP

Итоговый MVP — минимальная законченная версия учебного проекта. Помимо базового прототипа, для него обязательны:

- временная актуальность отношений и вычисление последовательности событий «до» и «после»;
- явные причинные отношения и различение последовательности и причинности;
- повторяющиеся наблюдения и расчёт частоты связей;
- старение значимости связей по согласованному правилу;
- интерактивная визуализация в Dash + Cytoscape, включая отображение частоты и значимости связей;
- обработка согласованного набора естественных вопросов словарями и правилами и формирование текстовых ответов;
- проверка перечисленных возможностей на общем наборе Н-101 с помощью pytest.

Далее «первая версия» означает базовый прототип. «Расширение» означает последующий этап разработки, а не необязательность возможности для итогового MVP. Конкретные правила расчётов и формулировки вопросов согласуются командой. Natasha остаётся необязательным инструментом.

Для работы в памяти используется NetworkX MultiDiGraph. SQLite — постоянное хранилище. Dash + Cytoscape отображает данные, полученные от ядра. Отдельные серверы для модулей не требуются: это части одного Python-приложения.

## 2. Общие правила

- Идентификаторы — непустые строки, уникальные среди вершин и связей. Они постоянны и не зависят от отображаемого названия.
- Технические типы и имена полей записываются на английском; подписи и ответы пользователю — на русском.
- Сообщения между модулями состоят из простых значений: строк, чисел, логических значений, списков и именованных полей. Такой формат совместим с JSON; объекты NetworkX и соединения SQLite между модулями не передаются.
- Время передаётся в ISO 8601 с часовым поясом, например `2026-11-10T10:00:00+05:00`; хранение и сравнение выполняются в UTC.
- Отсутствие необязательного поля означает отсутствие сведений, если для него явно не задано другое правило.
- Цвета, размеры и координаты — настройки представления, а не свойства оборудования или отношений.
- Неподдерживаемая операция или расширение вызывает понятную ошибку, а не молчаливое игнорирование.

## 3. Структура вершины

### 3.1. Минимальные поля

| Поле | Обязательность | Смысл |
|---|---|---|
| `id` | Обязательно | Постоянный идентификатор, например `equipment:n101` |
| `type` | Обязательно | Один из пяти типов из таблицы ниже |
| `label` | Обязательно | Подпись, например «Насос Н-101» |
| `properties` | Необязательно, по умолчанию пустой набор | Свойства конкретного типа; для измерений и событий обязательны отдельные поля внутри него |

| Тип | Что представляет | Поля внутри `properties` |
|---|---|---|
| `Equipment` | Экземпляр оборудования | Необязательное `equipment_kind`, например `pump` |
| `Component` | Экземпляр компонента | Необязательное `component_kind`, например `motor` |
| `Sensor` | Конкретный датчик | Необязательное `quantity`, например `temperature` |
| `Measurement` | Одно показание | Обязательные `quantity`, числовое `value`, `unit`, `observed_at` |
| `Event` | Одно событие эксплуатации | Обязательные `event_kind`, `occurred_at`; необязательное `ended_at` |

Обязательность свойств измерения и события действует только при создании соответствующего типа. Для создания насоса достаточно `id`, `type`, `label`.

Измерения не перезаписывают друг друга: новое показание — новая вершина. В первой версии событие имеет известное время начала; неточные и неизвестные даты требуют отдельного согласования. Если `ended_at` указан, он не может быть раньше `occurred_at`.

Измерение связывается с одним датчиком через `PRODUCED_MEASUREMENT` и с одним измеряемым объектом через `MEASURES`. Поле `quantity` датчика, если задано, должно совпадать с величиной измерения. Для демонстрации температура задаётся как `temperature` в `°C`; преобразование других единиц пока не требуется.

### 3.2. Необязательные поля для расширений

| Поле | Назначение |
|---|---|
| `aliases` | Дополнительные названия для языкового модуля |
| `description` | Текстовое пояснение |
| `source_ref` | Источник сведений |
| `created_at` | Время добавления записи; не заменяет время измерения или события |

Изменяющееся состояние оборудования не следует хранить только одним перезаписываемым свойством: для истории нужны события или отношения с периодом действия.

## 4. Структура связи

### 4.1. Минимальные поля

| Поле | Обязательность | Смысл |
|---|---|---|
| `id` | Обязательно | Постоянный идентификатор связи, например `edge:001` |
| `source` | Обязательно | ID начальной вершины |
| `target` | Обязательно | ID конечной вершины |
| `relation` | Обязательно | Тип отношения из общего словаря |

Начальная и конечная вершины должны существовать. Ядро проверяет допустимую пару типов. ID связи используется как ключ ребра в MultiDiGraph.

Уникальность отдельной связи определяется только её `id`. Разрешены как разные отношения одной пары вершин, так и несколько связей с одинаковыми `source`, `relation`, `target`, если они описывают разные факты или периоды действия. Для каждого такого факта создаётся новый `id`; ограничение уникальности по тройке полей в SQLite не вводится.

Ядро не объединяет связи автоматически по совпадению этой тройки. Вызывающий модуль отвечает за выбор ID нового факта и повторное использование ID при повторной передаче того же факта. Повторное подтверждение существующего факта учитывается как наблюдение его связи, а не как новая связь.

Повторная передача того же ID и тех же данных не меняет результат. Тот же ID с другим содержимым возвращает ошибку конфликта; обновление не выполняется скрыто.

### 4.2. Поля для расширений

| Поле | Когда понадобится | Правило |
|---|---|---|
| `properties` | Дополнительные сведения | Только согласованные командой свойства |
| `source_ref` | Происхождение утверждения | Обязательно при добавлении явного причинного отношения |
| `created_at` | Учёт времени записи | Не определяет время действия отношения |
| `time_scope` | Временная актуальность | `interval`, `timeless` или `unknown` |
| `valid_from` | Для `time_scope = interval` | Обязательное начало действия |
| `valid_to` | Для интервала | Необязательный конец; отсутствие означает открытый конец |
| `base_weight` | Старение | Начальная значимость от 0 до 1 |
| `decay_policy` | Старение | Идентификатор согласованного правила, включая `none` |

До включения временного расширения период действия не задаётся. После его включения у старых записей без временных полей считается `time_scope = unknown`, а не «действует всегда». `timeless` означает, что отношение принято не ограничивать периодом в рамках модели.

Для интервалов начало включается, конец не включается. `valid_to` должен быть позже `valid_from`. Результат проверки на дату может быть «действует», «не действует» или «время неизвестно»; неизвестное время не считается подтверждённой актуальностью.

Текущая значимость вычисляется для заданного момента, а не подменяет исходный вес. Старение само по себе не удаляет факт и не завершает его период действия.

## 5. Сохраняемые и вычисляемые отношения

### 5.1. Отношения, сохраняемые в графе

| Отношение | Начало → конец | Смысл | Этап |
|---|---|---|---|
| `HAS_COMPONENT` | Equipment → Component | Оборудование содержит компонент | Первая версия |
| `INSTALLED_ON` | Sensor → Equipment или Component | Датчик физически установлен на объекте | Первая версия |
| `MONITORS` | Sensor → Equipment или Component | Датчик контролирует объект | Первая версия |
| `PRODUCED_MEASUREMENT` | Sensor → Measurement | Датчик выдал показание | Первая версия |
| `MEASURES` | Measurement → Equipment или Component | Показание относится к объекту | Первая версия |
| `HAS_EVENT` | Equipment или Component → Event | Событие относится к объекту | Первая версия |
| `CAUSES` | Event → Event | Явно указано причинное влияние | Расширение |
| `NOT_CAUSES` | Event → Event | Явно указано отсутствие причинного влияния | Расширение, требует согласования |

Причинная связь требует основания в `source_ref`, например записи журнала. Отсутствие `CAUSES` означает «причина не указана», а не `NOT_CAUSES`. Противоречащие друг другу `CAUSES` и `NOT_CAUSES` для одной пары событий должны вызывать сообщение о конфликте.

### 5.2. Отношения, вычисляемые по данным

| Отношение | Как получается |
|---|---|
| `BEFORE` | Первое событие завершилось до начала второго; для точечного события используется `occurred_at` |
| `AFTER` | Обратное прочтение `BEFORE` |
| `AFTER_NOT_CAUSED_BY` | Событие B произошло после A и имеется явное `A NOT_CAUSES B` |

Вычисление выполняет модуль времени. При совпадении границ или перекрытии событий строгие `BEFORE` и `AFTER` не выдаются. Если длительность не задана, событие предварительно считается точечным. Этот выбор требует согласования для длительных событий с неизвестным завершением.

Вычисляемые отношения не записываются как обычные связи SQLite. Они возвращаются в ответе и могут отображаться отдельно. Для них указываются `relation`, `source`, `target`, признак `computed` и `based_on` — ID исходных событий и связей. Если визуализации нужен ID, он создаётся в отдельном пространстве `computed:`.

Последовательность не доказывает причинность. Из температурного показания также нельзя автоматически получить событие перегрева без согласованного порогового правила. Такие правила пока не входят в первую версию.

## 6. Повторяющиеся наблюдения и частота

Для расчёта частоты предлагается отдельный список наблюдений, сохраняемый в SQLite при включении расширения. Наблюдение — запись о том, что конкретное отношение было замечено или подтверждено; это не шестой тип вершины.

| Поле | Обязательность | Смысл |
|---|---|---|
| `id` | Обязательно | Уникальный ID наблюдения |
| `edge_id` | Обязательно | ID существующей сохраняемой связи |
| `observed_at` | Обязательно | Когда наблюдение произошло |
| `source_ref` | Необязательно | Источник наблюдения |

Повторная загрузка наблюдения с тем же ID не увеличивает счётчик. Просмотр графа и выполнение запроса не являются наблюдениями. Создание связи само по себе не создаёт наблюдение.

Предварительные вычисляемые показатели:

- `observation_count` — число наблюдений связи за указанный период;
- `frequency` — это число, делённое на длительность периода; результат обязательно содержит единицу, например «наблюдений в сутки»;
- `last_observed_at` — время последнего наблюдения, если оно есть.

Период задаётся как включённое начало и исключённый конец; его длительность должна быть положительной. Если наблюдений нет, счётчик равен нулю, но это не означает ложность отношения.

Повторяющиеся измерения имеют разные вершины и разные связи `PRODUCED_MEASUREMENT`. Частоту показаний датчика считают по группе этих связей. Частота подтверждений одной связи и частота однотипных событий — разные показатели; объединять их без отдельного правила нельзя.

## 7. Интерфейсы четырёх модулей

Интерфейсы ниже описывают входы и выходы, а не программные функции. В первой версии это вызовы внутри одного приложения.

| Модуль | Принимает | Возвращает | Ответственность |
|---|---|---|---|
| 1. Ядро и SQLite | Вершину, связь или структурированный запрос; позднее — наблюдение | Результат операции, записи графа или ошибку | Проверка типов и ссылок, сохранение, загрузка, поиск |
| 2. Время и причинность | Записи графа и временные условия | Проверки актуальности, вычисленные отношения, основания | Временные правила и проверка причинных утверждений |
| 3. Частота, старение и визуализация | Записи графа; позднее — наблюдения, период и момент расчёта | Показатели связей и элементы Cytoscape | Расчёты, оформление и отображение |
| 4. Естественный язык | Текст и доступные названия объектов; затем результат запроса | Структурированный запрос, уточняющий вопрос или текстовый ответ | Словари, правила, разрешение названий и объяснение результатов |

Только ядро изменяет SQLite и рабочий граф. После успешного сохранения оно обновляет представление NetworkX; при ошибке сохранения изменение не считается выполненным. Остальные модули получают данные для чтения. Постоянная запись из визуализации или языкового модуля также проходит через ядро.

Координацию выполняет простой обработчик приложения: получает вопрос, вызывает языковой модуль, передаёт запрос ядру и направляет результат для текста и отображения. Это не отдельный сервис. При подключении расширений обработчик передаёт данные модулям 2 и 3.

### 7.1. Минимальный структурированный запрос

| Поле | Обязательность | Смысл |
|---|---|---|
| `operation` | Обязательно | В первой версии: `get_node`, `neighbors`, `subgraph` |
| `subject_id` | Обязательно | Уже определённый ID объекта |
| `relation` | Необязательно | Ограничение по сохраняемому типу отношения |
| `direction` | Необязательно, по умолчанию `outgoing` | `outgoing`, `incoming` или `both` |

`get_node` возвращает одну вершину. `neighbors` возвращает непосредственных соседей и соединяющие их связи с учётом фильтра. `subgraph` возвращает исходную вершину, этих соседей и найденные связи; глубина в первой версии равна одному шагу. Поля `relation` и `direction` применяются только к двум последним операциям.

Структурированные операции сопоставляются интерфейсам ядра из раздела 7.3 следующим образом. Это преобразование выполняет обработчик приложения; отдельные дублирующие интерфейсы ядра не требуются.

| Операция запроса | Вызовы интерфейсов ядра | Результат |
|---|---|---|
| `get_node` | `find_nodes` с точным фильтром `id = subject_id` | Одна вершина, пустой список связей. Если поиск вернул `no_data`, обработчик преобразует его в `error` с `error_code = not_found`, поскольку запрос обращается к конкретному объекту |
| `neighbors` | `neighbors` с теми же `subject_id`, `relation` и `direction` | Результат ядра без изменения: соседи и все подходящие связи, включая параллельные; исходная вершина автоматически не добавляется |
| `subgraph` | Сначала `find_nodes` с `id = subject_id`, затем `neighbors` с теми же фильтрами и направлением | Исходная вершина, соседи без повторений по ID и все найденные связи. Если исходная вершина есть, но соседей нет, возвращается `ok` с одной вершиной и пустым списком связей |

Для `subgraph` отсутствие исходной вершины преобразуется в `error` с `not_found`, и поиск соседей не выполняется. Другие ошибки любого вызова передаются без подмены пустым результатом; частичный подграф не возвращается. Таким образом, `no_data` при поиске по фильтру и ошибка обращения к отсутствующему `subject_id` сохраняют разный смысл.

Расширения запроса: `valid_at` для актуальности; `event_time_from` и `event_time_to` для времени событий и измерений; `window_from` и `window_to` для частоты; `evaluation_time` для старения. Операции `event_order`, `causes`, `frequency` добавляются вместе с соответствующим расширением. Детали их входов утверждаются перед реализацией.

Пример без программного кода: вопрос «Какие компоненты у насоса Н-101?» превращается в запрос с `operation = neighbors`, `subject_id = equipment:n101`, `relation = HAS_COMPONENT`, `direction = outgoing`.

Если название соответствует нескольким объектам, модуль 4 запрашивает уточнение. Если объект не найден, он сообщает об этом. Произвольный SQL или выражения NetworkX из пользовательского текста не создаются.

### 7.2. Общий результат операции

| Поле | Смысл |
|---|---|
| `status` | `ok`, `no_data`, `ambiguous` или `error` |
| `nodes`, `edges` | Найденные вершины и сохраняемые связи; списки могут быть пустыми |
| `message` | Понятное пояснение при отсутствии данных, неоднозначности или ошибке |
| `error_code` | При ошибке: например `invalid_data`, `not_found`, `conflict`, `unsupported_operation`, `storage_error` |

При расширении результата добавляются `computed_relations`, показатели связей и применённые параметры расчёта. Вычисляемые отношения не смешиваются со списком `edges`.

Синтаксически корректный поиск без совпадений возвращает `no_data`; обращение к несуществующему `subject_id` — ошибку `not_found`. Языковой модуль строит ответ только по результату. Если причинные данные отсутствуют, ответ — «Причина в данных не указана».

### 7.3. Конкретные интерфейсы ядра

Имена ниже обозначают операции договора, а не готовый программный код. Все операции возвращают общий результат из раздела 7.2. При `error` передаются `error_code` и `message`; частичный успешный результат не выдаётся. Ошибки сохранения не должны оставлять частично записанные данные.

#### Создание вершины — `create_node`

| Пункт | Договор |
|---|---|
| Назначение | Добавить одну вершину с проверкой её структуры |
| Вход | Запись вершины: обязательные `id`, `type`, `label`; необязательные поля раздела 3. Для Measurement и Event проверяются обязательные свойства их типа |
| Результат | `status = ok`, `nodes` содержит созданную или уже существующую вершину, `edges` пуст; `effect = created` либо `already_exists` |
| Ошибки | `invalid_data` — пустое обязательное поле, неизвестный тип или некорректные свойства; `conflict` — ID занят записью другого содержания или связью; `storage_error` — запись в SQLite не выполнена |

Повторная передача того же ID с теми же данными возвращает `already_exists`, не создаёт новую вершину и не меняет исходную запись. Для сравнения отсутствие `properties` и пустой набор свойств считаются одинаковыми. Серверные поля, например автоматически заполненный `created_at`, не требуется повторять во входе.

#### Создание связи — `create_edge`

| Пункт | Договор |
|---|---|
| Назначение | Добавить одну сохраняемую направленную связь |
| Вход | Запись связи: обязательные `id`, `source`, `target`, `relation`; необязательные поля раздела 4 при поддержке соответствующего расширения |
| Результат | `status = ok`, `edges` содержит созданную или уже существующую связь, `nodes` пуст; `effect = created` либо `already_exists` |
| Ошибки | `invalid_data` — неизвестное сохраняемое отношение, недопустимая пара типов или некорректный период; `not_found` — нет начальной или конечной вершины; `conflict` — ID занят записью другого содержания или вершиной, либо факты противоречат друг другу по согласованным правилам; `unsupported_operation` — запрошенное расширение пока не реализовано; `storage_error` — запись в SQLite не выполнена |

Совпадение `source`, `relation`, `target` при новом ID не является ошибкой или основанием вернуть старую связь. Повторная передача того же ID и тех же данных возвращает `already_exists`. Вычисляемые `BEFORE` и `AFTER` через этот интерфейс не создаются. Поля расширений не игнорируются молча.

#### Поиск вершин — `find_nodes`

| Пункт | Договор |
|---|---|
| Назначение | Получить вершины по идентификатору, типу или названию |
| Вход | Необязательные фильтры `id`, `type`, `text`; без фильтров возвращаются все вершины базового демонстрационного графа |
| Результат | `status = ok` и список `nodes`, отсортированный по ID; `edges` пуст. При отсутствии совпадений — `status = no_data` и пустые списки |
| Ошибки | `invalid_data` — неизвестный тип вершины, неверный тип фильтра или неподдерживаемый фильтр |

Фильтр `id` проверяется на точное совпадение, `type` — на точное значение из словаря. `text` ищется как подстрока без учёта регистра в `label` и в `aliases`, если они есть. Несколько фильтров применяются одновременно по правилу «и». Пустой `text` считается отсутствующим фильтром. Несколько совпадений — обычный результат поиска, а не ошибка: уточнение естественного вопроса выполняет модуль 4. Неизвестный ID в поисковом фильтре даёт `no_data`, в отличие от обращения к обязательному `subject_id`.

#### Получение соседей — `neighbors`

| Пункт | Договор |
|---|---|
| Назначение | Получить непосредственных соседей и все подходящие сохраняемые связи на расстоянии одного шага |
| Вход | Обязательное `subject_id`; необязательные `relation` и `direction`, по умолчанию `outgoing` |
| Результат | `status = ok`, в `nodes` — соседи без повторений, в `edges` — все подходящие связи с отдельными ID, включая одинаковые тройки `source`, `relation`, `target`. Списки сортируются по ID. При отсутствии соседей — `no_data` |
| Ошибки | `invalid_data` — некорректное направление или неизвестное сохраняемое отношение; `not_found` — исходная вершина отсутствует; `unsupported_operation` — запрошены ещё не поддерживаемые временные или вычисляемые условия |

`outgoing` выбирает связи из вершины, `incoming` — в вершину, `both` — оба направления. Одна связь не повторяется в результате `both`. Исходная вершина не добавляется в список соседей автоматически; для получения её вместе с окружением используется `subgraph`.

#### Сохранение графа — `save_graph`

| Пункт | Договор |
|---|---|
| Назначение | Явно сохранить согласованный текущий граф ядра в настроенную SQLite и подтвердить завершение записи |
| Вход | Текущий граф, которым владеет ядро; внешних `nodes`, `edges` и произвольного пути к базе во входе нет |
| Результат | `status = ok`, `effect = saved`, `saved_node_count` и `saved_edge_count`; `nodes` и `edges` пусты. Счётчики показывают общий размер сохранённого графа, а не число новых записей |
| Ошибки | `invalid_data` — внутренний граф нарушает договор; `storage_error` — SQLite недоступна, запись или завершение транзакции не выполнены |

В базовом прототипе `create_node` и `create_edge` сохраняют изменения сразу. `save_graph` — явная контрольная операция для демонстрации и будущей пакетной загрузки, а не обязательный второй шаг после каждого создания. Она работает с текущим состоянием ядра, сохраняет постоянные ID и не создаёт дубликатов при повторном вызове. Пакетный режим с несохранёнными изменениями пока не вводится. Сохраняемый снимок включает все записи постоянного хранения, поддерживаемые на данном этапе; после подключения наблюдений они сохраняются вместе со своими связями. Вычисляемые отношения и стили визуализации не записываются как факты графа.

Ни один внешний модуль не изменяет рабочий граф напрямую. Если чтение требует обращения к SQLite и оно не удалось, поисковые операции также могут вернуть `storage_error`.

### 7.4. Восстановление графа при запуске

До обработки запросов ядро открывает SQLite по настроенному пути и подготавливает рабочий MultiDiGraph. SQLite остаётся постоянным источником данных; загрузка не создаёт новые ID и не вызывает операции создания фактов повторно.

| Состояние хранилища | Поведение приложения |
|---|---|
| Файл базы отсутствует | Создать SQLite с необходимой структурой и пустой рабочий граф. После успешной инициализации разрешить операции. Демонстрационные данные автоматически не добавлять |
| База существует и содержит сохранённые данные | Проверить структуру хранилища, прочитать вершины, затем связи и восстановить их атрибуты и постоянные ID. После подключения наблюдений загрузить и их. Проверить данные по договору и только после успешной загрузки всего набора сделать граф доступным приложению |
| База корректна, но записей нет | Запустить приложение с пустым графом; это штатный случай, а не ошибка |
| Ошибка открытия, чтения или восстановления | Сообщить об ошибке и не переходить к обработке запросов и сохранению графа. Не подменять повреждённые или недоступные данные пустым графом и не перезаписывать существующую базу |

Ошибки доступа или чтения сообщаются как `storage_error`; нарушение договора в загруженных записях — как `invalid_data` с пояснением. Неподдерживаемая структура существующей базы считается ошибкой загрузки, а не отсутствием базы: автоматическое пересоздание не выполняется. Неудачная попытка создания новой базы также останавливает инициализацию.

Загрузка сначала формирует и проверяет внутренний граф, недоступный другим модулям. Связь с отсутствующей вершиной или потеря обязательного атрибута не допускает частичного запуска. Вычисляемые отношения и показатели пересчитываются при необходимости, а не восстанавливаются как сохраняемые факты. После успешного запуска действуют прежние правила немедленного сохранения и операции `save_graph`.

Связи `edge:002` и `edge:002b` показывают два отношения одной пары: датчик установлен на двигателе и контролирует его. Установка и контроль хранятся отдельно: одно не выводится автоматически из другого. Это уточнение заменяет предложенное ранее общее `HAS_SENSOR` и требует утверждения командой.

### 8.3. Примеры расширений

- Для `edge:002`: `time_scope = interval`, `valid_from = 2026-11-01T09:00:00+05:00`, конец открыт.
- Пример повторной установки: у `edge:002` конец можно задать как `valid_to = 2026-11-12T09:00:00+05:00`, а для повторной установки создать `edge:010` с теми же `source = sensor:t101`, `relation = INSTALLED_ON`, `target = component:m101`, но с `valid_from = 2026-11-14T09:00:00+05:00`. Это два разных факта с разными ID. Повторная передача `edge:010` не создаёт третью связь.
- Два наблюдения `observation:001` и `observation:002` подтверждают `edge:002` соответственно в `2026-11-10T09:00:00+05:00` и `2026-11-10T15:00:00+05:00`. В обоих случаях источник — `demo:inspection-log`.
- За период от `2026-11-10T00:00:00+05:00` до `2026-11-11T00:00:00+05:00` получаем два подтверждения и частоту два наблюдения в сутки. Повторная загрузка `observation:001` результат не меняет.
- Временной модуль вычисляет `event:overheat-001 BEFORE event:stop-001` из времени событий; эта связь не сохраняется.
- В причинном расширении можно добавить `edge:009`: `event:overheat-001 CAUSES event:stop-001`, `source_ref = demo:operation-log`. Основанием служит явное утверждение учебного журнала, а не порядок событий.

Ожидаемый ответ на вопрос о компонентах Н-101 — «Электродвигатель М-101». После включения временного расширения ответ о последовательности — «Перегрев произошёл раньше остановки». Ответ о причине возможен только после добавления причинного утверждения.

1. Достаточно ли пяти типов? Для цеха из примера README потребуется отдельный тип места; в текущий договор он не включён.
2. Подтверждаем ли словарь сохраняемых отношений и вычисление `BEFORE`/`AFTER` вместо хранения зеркальных связей?

7. Как трактовать неизвестные даты, пересекающиеся события и незавершённые длительные события? Нужна только история действия отношений или также история исправления записей?
8. Какие основания допустимы для причинности? Нужен ли `NOT_CAUSES`, кто имеет право его утверждать и как разрешаются конфликты?
9. Какие отношения стареют, по какому правилу и от какого момента? Отсутствие новых наблюдений не должно автоматически отменять факт установки компонента.

## 10. Проверка договора перед реализацией

Команда рассматривает документ и утверждает минимальные поля, словарь отношений и один общий набор Н-101. Затем каждый модуль проверяется на этих же данных.

Основные сценарии для будущих проверок базового прототипа: сохранение и загрузка без потери ID и типов; запрет связи с отсутствующей вершиной; несколько отношений одной пары; несколько фактов с одинаковыми `source`, `relation`, `target` и разными ID; отсутствие дубликатов при повторной передаче того же ID; поиск и получение соседей без потери параллельных связей.

Проверка сохранения и восстановления в будущих тестах pytest:

1. Запустить ядро с отсутствующей базой во временном каталоге и убедиться, что создано пустое хранилище и приложение готово к работе.
2. Создать небольшой набор Н-101, включая две связи с одинаковыми `source`, `relation`, `target`, но разными ID; выполнить `save_graph` и закрыть ядро и соединение с SQLite.
3. Запустить новый экземпляр ядра с той же базой. Сравнить вершины и связи по ID и всем сохраняемым атрибутам, проверить число записей и результат `neighbors`. Порядок внутренних элементов NetworkX не является критерием равенства.
4. Повторить сохранение и запуск: количество фактов не должно увеличиться. После подключения наблюдений включить их ID и атрибуты в ту же проверку.
5. Отдельно проверить корректную пустую базу и ошибки загрузки: недоступный файл, повреждённое хранилище или некорректные записи должны давать понятную ошибку без частичного запуска и перезаписи исходных данных.

Для готовности итогового MVP дополнительно обязательны проверки повторных наблюдений и частоты, границ временных интервалов, различия между последовательностью и причинностью, старения, отображения графа и ответов на согласованные естественные вопросы. Завершение базового прототипа не означает завершение MVP.

Изменения обязательных полей и смысла отношений обсуждаются всей командой и отражаются в версии договора. Дополнительные поля не должны становиться обязательными для первой версии без отдельного решения.
